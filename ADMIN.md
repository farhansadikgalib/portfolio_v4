# Portfolio console

The portfolio now includes a private console at `/admin`. Visitors can view the public site without signing in. Editing content, previewing drafts, uploading images, and publishing all require an authenticated owner session.

## Run locally

Use Node.js 22 or newer (Node.js 24 LTS is recommended).

```sh
npm install
npm run admin:setup
npm run dev
```

The setup command asks for your email and a password of at least 12 characters. Password input is hidden. There is no default password and no public registration endpoint. Open **http://localhost:5173/admin**, then sign in with the account you created.

Use the Node server for the console and managed portfolio. VS Code Live Server on port 5500 cannot run authentication, save content, or handle uploads.

## Edit and publish

- **Page builder:** move sections with drag and drop or the Move up/Move down controls, hide sections, adjust spacing, and add text, image, or call-to-action sections. Built-in sections can be hidden and reordered; their original layout remains available.
- **Content:** edit site/contact settings, or choose a section and edit its text, links, and images. Text fields are plain text, keeping the site's markup safe and its typography consistent.
- **Projects:** add, edit, or remove projects; choose featured apps; update descriptions, responsibilities, links, icons, and screenshot galleries.
- **Media:** upload PNG, JPEG, or WebP images, choose existing images, and delete unused uploads. Uploaded images are decoded and converted to WebP. The upload limit is 8 MiB. Bundled original assets remain available and cannot be deleted from disk through the console.
- **Account:** change your login password and manage unpublished drafts.

**Save draft** stores your work without changing the public site. **Preview** shows the saved draft in an authenticated preview. **Publish** makes the saved draft public. **Discard draft** restores the last published content. Unsaved browser edits must be saved before leaving the console.

To replace a hero image, select an image from the media picker or upload one. Choose **Contain** to show the complete image or **Cover** to fill the frame. The original supplied screenshots use a special crop that remains available through **Original**. Removing an image from content does not delete the underlying media file.

An uploaded image cannot be deleted while it is referenced by either the draft or published content. Remove or replace its references, save and publish, then delete it from Media. This keeps the live site from ending up with missing images.

## Deployment and backups

The console requires a running Node server with **persistent writable storage**. Uploading only `dist/` to a static host does not deploy the CMS. Serverless hosts with ephemeral filesystems need a separate database/object-storage integration before deploying this backend there.

```sh
npm ci
npm run check
npm test
npm run build
npm start
```

Environment variables:

| Variable | Purpose |
| --- | --- |
| `PORT` | HTTP port; defaults to 5173 |
| `HOST` | Listening interface; use `0.0.0.0` behind a production reverse proxy |
| `SITE_ORIGIN` | Exact public origin, such as `https://portfolio.example.com` |
| `CMS_DATA_DIR` | Absolute path to persistent CMS storage; defaults to `.cms-data` |
| `NODE_ENV` | Set to `production` for deployment |

Serve production traffic through HTTPS and set `SITE_ORIGIN` to the exact HTTPS origin. Keep `.cms-data` (or your configured directory) outside any separately served public directory. Back up the entire data directory: it contains owner credentials, content state, and uploaded media. Do not commit it, copy it into `dist/`, or make it publicly downloadable.

For a safe file backup, stop the Node process, copy the data directory, then restart it. Restore the directory with the process stopped. Rebuilding the website does not reset CMS storage. Sessions expire and restarting the server requires signing in again.

If you lose your password, use `npm run admin:setup -- --reset` from a trusted server terminal. This is an explicit local owner reset, not an unauthenticated web endpoint.

## Implementation

The server authenticates every admin API route; the browser alone cannot grant access. Sessions use server-generated tokens in HttpOnly, SameSite cookies. Mutations require a session-bound CSRF token and same-origin checks. Credentials use salted scrypt hashing, login attempts are rate-limited, and public content never includes credential or session data.

Content is validated before storage, revisions protect against overwriting another open editor's work, and content snapshots are written atomically. Images have bounded file/pixel sizes and are decoded before storage. Uploaded names are generated by the server rather than used as filesystem paths.

Relevant design references: [OWASP session management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [file upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html), and [Sharp input limits](https://sharp.pixelplumbing.com/api-constructor/).
